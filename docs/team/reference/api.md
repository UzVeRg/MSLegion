# Справочник HTTP API MSLegion

Текущий API предназначен для разработки и административной проверки backend без
пользовательского интерфейса.

## Общий формат

Каждый HTTP-ответ содержит заголовок `X-Request-ID`.

Клиент может передать собственный `X-Request-ID`, если значение состоит из
латинских букв, цифр и символов `.`, `_`, `:`, `-` и не длиннее 128 символов.
Иначе backend генерирует идентификатор самостоятельно.

Ошибки возвращаются в едином формате. Используйте поле `code` для обработки ошибок в клиентском коде. Поле `message` содержит пояснение для человека. Машиночитаемое описание маршрутов, схем ключей и ответов доступно по `/openapi.json`. Например, отсутствующий обязательный параметр даёт HTTP 422 со следующим телом (поле `details` с подробностями опущено).

```json
{
  "error": {
    "code": "validation_error",
    "message": "Запрос не прошёл проверку",
    "request_id": "..."
  }
}
```

## Состояние приложения

### `GET /health`

Проверяет, что процесс FastAPI запущен.

Успех: `200 OK`.

### `GET /ready`

Проверяет, что приложение может прочитать столбцы моделей пользователей, сессий, сообществ, членства, серверов и событий в PostgreSQL. Проверка не сканирует данные.

Успех: `200 OK`.
Если база данных или ожидаемая схема недоступна: `503 Service Unavailable`.

## Вход и сессии

### `POST /api/v1/auth/telegram`

Принимает JSON с полем `init_data`. Передайте в нём исходную строку из `Telegram.WebApp.initData`. При успехе ответ `200 OK` содержит `access_token`, `token_type` со значением `bearer` и `expires_at` в UTC. Сессия действует 8 часов. Храните токен в памяти Mini App и передавайте его по HTTPS в заголовке `Authorization: Bearer <access_token>`.

- `401 Unauthorized` — данные Telegram недействительны или просрочены.
- `403 Forbidden` — требуется подтверждение привязки или доступ пользователя отключён.
- `503 Service Unavailable` — в серверном окружении отсутствует `TELEGRAM_BOT_TOKEN`.

### `GET /api/v1/auth/me`

Возвращает профиль владельца предъявленной сессии с кодом `200 OK`. Состав полей совпадает с ответом `GET /api/v1/users/{user_id}`. UUID берётся из сессии на сервере.

### `POST /api/v1/auth/logout`

Отзывает предъявленную сессию и возвращает `204 No Content`. При недействительном, просроченном или уже отозванном токене профиль и выход возвращают `401 Unauthorized` с кодом `invalid_session` и заголовком `WWW-Authenticate: Bearer`.

## Сообщества

Все маршруты требуют действующей пользовательской сессии. Для пользователя вне сообщества запрос к нему возвращает `404 community_not_found`. Для участника, вызвавшего операцию владельца, возвращается `403 community_owner_required`.

- `POST /api/v1/communities` принимает `{"name":"Название"}` и возвращает `201` с `id`, `name` и `owner_id`. Владельцем становится пользователь из сессии.
- `GET /api/v1/communities` возвращает список сообществ владельца или участника. `GET /api/v1/communities/{community_id}` возвращает одно доступное сообщество.
- `GET /api/v1/communities/{community_id}/members` возвращает владельцу список записей с `user_id`. Сам владелец указан в `owner_id` карточки сообщества.
- `PUT /api/v1/communities/{community_id}/members/{user_id}` добавляет существующего пользователя по внутреннему UUID. `DELETE` по тому же адресу исключает участника. Успех и повтор возвращают `204`. Попытка исключить владельца возвращает `409 community_owner_removal`.

Списки используют `offset` от 0 и `limit` от 1 до 100. По умолчанию возвращается до 50 записей.

### Серверы сообщества

- `GET /api/v1/communities/{community_id}/servers` возвращает владельцу и участникам страницу серверов сообщества. Параметры пагинации те же.
- `POST /api/v1/communities/{community_id}/servers` регистрирует сервер по запросу владельца. Тело содержит `name`, `host` и целочисленный `port` от 1 до 65535. Передавайте DNS-имя или IP-адрес отдельно от порта. Успех возвращает `201` с `id`, `community_id`, `name`, `host` и `port`. Повтор адреса в том же сообществе возвращает `409 community_server_conflict`.
- `DELETE /api/v1/communities/{community_id}/servers/{server_id}` удаляет сервер по запросу владельца и возвращает `204`. Отсутствующий в этом сообществе сервер даёт `404 community_server_not_found`.

## Пользователи

Все операции по префиксу `/api/v1/users` требуют `X-Admin-Key`. Это служебное управление записями. При отсутствии или несовпадении требуемого ключа защищённые маршруты возвращают `401 Unauthorized`.

### `POST /api/v1/users`

Создаёт пользователя.

Пример тела:

```json
{
  "telegram_id": 123456789,
  "display_name": "Test User"
}
```

`telegram_id` опционален. Допустимый диапазон — от 1 до 9 223 372 036 854 775 807 включительно. Внутренним идентификатором пользователя является UUID. Указанный вручную `telegram_id` требует подтверждения перед входом через Telegram.

Успех: `201 Created`.
Повторный `telegram_id`: `409 Conflict`.

### `GET /api/v1/users`

Возвращает список пользователей.

Параметры запроса:

- `offset` — от `0` до `9223372036854775807`;
- `limit` — от `1` до `100`, по умолчанию `50`.

Успех: `200 OK`.

### `GET /api/v1/users/{user_id}`

Возвращает одного пользователя по внутреннему UUID.

Успех: `200 OK`.
Пользователь не найден: `404 Not Found`.

### `PUT /api/v1/users/{user_id}/telegram/confirmation`

Подтверждает существующую привязку. Администратор предварительно сверяет принадлежность записи, затем передаёт её UUID в пути и идентификатор Telegram в теле запроса, например `{"telegram_id": 123456789}`.

- `204 No Content` — привязка подтверждена. Повтор с теми же идентификаторами также возвращает `204`.
- `404 Not Found` — пользователь не найден.
- `409 Conflict` — у пользователя нет указанного Telegram ID.

## Входящие события интеграций

### `POST /api/v1/callbacks/events`

Требует заголовок `X-Callback-Key`.

Пример тела:

```json
{
  "source": "manual-test",
  "event_id": "event-001",
  "event_type": "ping",
  "payload": {
    "value": 1
  }
}
```

Успех: `200 OK`.

Ключ события — пара `source` и `event_id`. Повтор того же типа и содержимого возвращает `200 OK`, `duplicate: true` и UUID исходной записи, в том числе при одновременной доставке. Тип сравнивается после нормализации, а содержимое — по правилам равенства PostgreSQL JSONB. Например, порядок ключей объекта не влияет на результат. При другом типе или содержимом backend возвращает `409 event_id_conflict` и сохраняет первоначальную запись.

В строках и ключах JSON допустимы символы Unicode, кроме NUL. Числа должны быть конечными. При ошибке ввода backend возвращает HTTP 422 с расположением, типом и описанием ошибки.

## Администрирование

Административные маршруты требуют заголовок `X-Admin-Key`.

### `GET /api/v1/admin/status`

Возвращает состояние базы данных и количество основных записей. Если запрос счётчиков не удался, ответ содержит HTTP 200, `database: "unavailable"` и `null` в обоих счётчиках. Для проверки готовности используйте `/ready`.

### `GET /api/v1/admin/callbacks`

Возвращает историю входящих событий интеграций.

Поддерживает `offset`, `limit`, `source` и `event_type`. Списки событий и пользователей отсортированы по убыванию времени, при совпадении времени — по убыванию UUID. Между запросами с `offset` новые записи могут сдвинуть границу страницы.
