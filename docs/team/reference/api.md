# Справочник HTTP API MSLegion

Текущий API предназначен для разработки и административной проверки backend без
пользовательского интерфейса.

## Общий формат

Каждый HTTP-ответ содержит заголовок `X-Request-ID`.

Клиент может передать собственный `X-Request-ID`, если значение состоит из
латинских букв, цифр и символов `.`, `_`, `:`, `-` и не длиннее 128 символов.
Иначе backend генерирует идентификатор самостоятельно.

Ошибки возвращаются в едином формате. Используйте поле `code` для обработки ошибок в клиентском коде. Поле `message` содержит пояснение для человека. Машиночитаемое описание маршрутов, схем ключей и ответов доступно по `/openapi.json`. Например, отсутствующий обязательный параметр даёт HTTP 422 со следующим телом (поле `details` с подробностями опущено).

```json
{
  "error": {
    "code": "validation_error",
    "message": "Запрос не прошёл проверку",
    "request_id": "..."
  }
}
```

## Состояние приложения

### `GET /health`

Проверяет, что процесс FastAPI запущен.

Успех: `200 OK`.

### `GET /ready`

Проверяет, что приложение может прочитать столбцы моделей пользователей, сессий, сообществ, членства, серверов и событий в PostgreSQL, включая внутренний журнал. Проверка не сканирует данные.

Успех: `200 OK`.
Если база данных или ожидаемая схема недоступна: `503 Service Unavailable`.

## Вход и сессии

### `POST /api/v1/auth/telegram`

Принимает JSON с полем `init_data`. Передайте в нём исходную строку из `Telegram.WebApp.initData`. При успехе ответ `200 OK` содержит `access_token`, `token_type` со значением `bearer` и `expires_at` в UTC. Сессия действует 8 часов. Храните токен в памяти Mini App и передавайте его по HTTPS в заголовке `Authorization: Bearer <access_token>`.

- `401 Unauthorized` — данные Telegram недействительны или просрочены.
- `403 Forbidden` — требуется подтверждение привязки или доступ пользователя отключён.
- `503 Service Unavailable` — в серверном окружении отсутствует `TELEGRAM_BOT_TOKEN`.

### `GET /api/v1/auth/me`

Возвращает профиль владельца предъявленной сессии с кодом `200 OK`. UUID берётся из сессии на сервере. Ответ содержит поля `GET /api/v1/users/{user_id}` и булево `telegram_notifications_enabled`.

### `PUT /api/v1/auth/me/telegram-notifications`

Сохраняет настройку личных уведомлений владельца сессии. Тело и ответ содержат булево поле `enabled`. По умолчанию уведомления отключены. Отправка предназначена для переходов между известными статусами серверов сообществ, которыми пользователь владеет.

### `POST /api/v1/auth/logout`

Отзывает предъявленную сессию и возвращает `204 No Content`. При недействительном, просроченном или уже отозванном токене профиль и выход возвращают `401 Unauthorized` с кодом `invalid_session` и заголовком `WWW-Authenticate: Bearer`.

## Сообщества

Все маршруты требуют действующей пользовательской сессии. Для пользователя вне сообщества запрос к нему возвращает `404 community_not_found`. Для участника, вызвавшего операцию владельца, возвращается `403 community_owner_required`.

- `POST /api/v1/communities` принимает `{"name":"Название"}` и возвращает `201` с `id`, `name` и `owner_id`. Владельцем становится пользователь из сессии.
- `GET /api/v1/communities` возвращает список сообществ владельца или участника. `GET /api/v1/communities/{community_id}` возвращает одно доступное сообщество.
- `GET /api/v1/communities/{community_id}/members` возвращает владельцу список записей с `user_id`. Сам владелец указан в `owner_id` карточки сообщества.
- `PUT /api/v1/communities/{community_id}/members/{user_id}` добавляет существующего пользователя по внутреннему UUID. `DELETE` по тому же адресу исключает участника. Успех и повтор возвращают `204`. Попытка исключить владельца возвращает `409 community_owner_removal`.

Списки используют `offset` от 0 и `limit` от 1 до 100. По умолчанию возвращается до 50 записей.

### Серверы сообщества

- `GET /api/v1/communities/{community_id}/servers` возвращает владельцу и участникам страницу серверов сообщества. Параметры пагинации те же. Поля `online` и `status_observed_at` содержат последнее обработанное наблюдение или `null`, пока наблюдений нет.
- `POST /api/v1/communities/{community_id}/servers` регистрирует сервер по запросу владельца. Тело содержит `name`, `host` и целочисленный `port` от 1 до 65535. Передавайте DNS-имя или IP-адрес отдельно от порта. Успех возвращает `201` с `id`, `community_id`, `name`, `host` и `port`. Повтор адреса в том же сообществе возвращает `409 community_server_conflict`.
- `DELETE /api/v1/communities/{community_id}/servers/{server_id}` удаляет сервер по запросу владельца и возвращает `204`. Отсутствующий в этом сообществе сервер даёт `404 community_server_not_found`.

### `GET /api/v1/communities/{community_id}/statistics`

Возвращает владельцу и участникам счётчики `members` с учётом владельца, `servers`, `online`, `offline` и `unobserved`.

### `GET /api/v1/communities/{community_id}/statistics/activity`

Возвращает владельцу и участникам дневные суммы записанных внутренних событий. Параметр `days` принимает от 1 до 90 дней, по умолчанию 30, включая сегодняшний день UTC. Поля `from_date` и `to_date` задают диапазон включительно. Массив `activity` содержит `day`, `event_type` и `count` для дат и типов с событиями.

### Публикации сообщества

- `GET /api/v1/communities/{community_id}/posts` возвращает доступную участнику страницу публикаций, новые записи первыми. Поля ответа — `id`, `title`, `body`, `created_at` и `has_image`.
- `POST /api/v1/communities/{community_id}/posts` создаёт публикацию по запросу владельца. Принимает `title` до 128 символов и `body` до 8192 символов. Ответ — `201`. Тело HTTP-запроса больше 128 КиБ даёт `413`.
- `PUT /api/v1/communities/{community_id}/posts/{post_id}/image` принимает необработанные байты изображения от владельца и возвращает `204`. Поддерживаются PNG, JPEG и WebP. Изображение больше 2 МиБ даёт `413`, неподдерживаемая сигнатура — `415`. Повторная загрузка заменяет изображение.
- `GET /api/v1/communities/{community_id}/posts/{post_id}/image` скачивает изображение как вложение. Требуется пользовательская сессия участника или владельца.
- `DELETE /api/v1/communities/{community_id}/posts/{post_id}` удаляет публикацию вместе с изображением по запросу владельца. Ответ — `204`.

## Пользователи

Все операции по префиксу `/api/v1/users` требуют `X-Admin-Key`. Это служебное управление записями. При отсутствии или несовпадении требуемого ключа защищённые маршруты возвращают `401 Unauthorized`.

### `POST /api/v1/users`

Создаёт пользователя.

Пример тела:

```json
{
  "telegram_id": 123456789,
  "display_name": "Test User"
}
```

`telegram_id` опционален. Допустимый диапазон — от 1 до 9 223 372 036 854 775 807 включительно. Внутренним идентификатором пользователя является UUID. Указанный вручную `telegram_id` требует подтверждения перед входом через Telegram.

Успех: `201 Created`.
Повторный `telegram_id`: `409 Conflict`.

### `GET /api/v1/users`

Возвращает список пользователей.

Параметры запроса:

- `offset` — от `0` до `9223372036854775807`;
- `limit` — от `1` до `100`, по умолчанию `50`.

Успех: `200 OK`.

### `GET /api/v1/users/{user_id}`

Возвращает одного пользователя по внутреннему UUID.

Успех: `200 OK`.
Пользователь не найден: `404 Not Found`.

### `PUT /api/v1/users/{user_id}/telegram/confirmation`

Подтверждает существующую привязку. Администратор предварительно сверяет принадлежность записи, затем передаёт её UUID в пути и идентификатор Telegram в теле запроса, например `{"telegram_id": 123456789}`.

- `204 No Content` — привязка подтверждена. Повтор с теми же идентификаторами также возвращает `204`.
- `404 Not Found` — пользователь не найден.
- `409 Conflict` — у пользователя нет указанного Telegram ID.

## Входящие события интеграций

### `POST /api/v1/callbacks/events`

Требует заголовок `X-Callback-Key`.

Пример тела:

```json
{
  "source": "manual-test",
  "event_id": "event-001",
  "event_type": "ping",
  "payload": {
    "value": 1
  }
}
```

Успех: `200 OK`.

Ключ события — пара `source` и `event_id`. Повтор того же типа и содержимого возвращает `200 OK`, `duplicate: true` и UUID исходной записи, в том числе при одновременной доставке. Тип сравнивается после нормализации, а содержимое — по правилам равенства PostgreSQL JSONB. Например, порядок ключей объекта не влияет на результат. При другом типе или содержимом backend возвращает `409 event_id_conflict` и сохраняет первоначальную запись.

В строках и ключах JSON допустимы символы Unicode, кроме NUL. Числа должны быть конечными. При ошибке ввода backend возвращает HTTP 422 с расположением, типом и описанием ошибки.

Источник `server-status` зарезервирован. Общий маршрут возвращает `403 callback_source_forbidden` при попытке использовать этот источник.

### `POST /api/v1/callbacks/server-status`

Принимает через `X-Callback-Key` отдельный ключ `SERVER_STATUS_API_KEY`. Тело содержит `event_id`, внутренний UUID зарегистрированного `server_id`, булево `online` и `observed_at` с часовым поясом. Сервер назначает источник `server-status` и тип `server.status`. Время наблюдения может опережать сервер не более чем на минуту.

`200` подтверждает сохранение, `duplicate: true` обозначает повтор уже полученного наблюдения. Несовпадающее содержимое для того же `event_id` возвращает `409 event_id_conflict`. По обычному ключу приёма доступ закрыт.

Записи, которые до миграции приняли с таким же `source` через общий маршрут, остаются в истории в отдельной области дедупликации.

## Администрирование

Административные маршруты требуют заголовок `X-Admin-Key`.

### `GET /api/v1/admin/status`

Возвращает состояние базы данных и количество основных записей. Если запрос счётчиков не удался, ответ содержит HTTP 200, `database: "unavailable"` и `null` в обоих счётчиках. Для проверки готовности используйте `/ready`.

### `GET /api/v1/admin/callbacks`

Возвращает историю входящих событий интеграций.

Поддерживает `offset`, `limit`, `source` и `event_type`. Списки событий и пользователей отсортированы по убыванию времени, при совпадении времени — по убыванию UUID. Между запросами с `offset` новые записи могут сдвинуть границу страницы.

Поле `processing_state` показывает состояние наблюдения: `pending`, `applied`, `ignored` для устаревшего наблюдения либо `rejected` для недопустимых данных или отсутствующего сервера. У обычных и ранее сохранённых событий поле равно `null`.

### `POST /api/v1/admin/callbacks/process`

Обрабатывает до `limit` ожидающих наблюдений. По умолчанию 50, допустимо от 1 до 100. Ответ содержит счётчики `applied`, `ignored` и `rejected` для этого вызова. Если одна транзакция завершилась сбоем, её событие остаётся в очереди и следующий вызов продолжает обработку. Уже завершённые события повторно не обрабатываются.

### `GET /api/v1/admin/callbacks/processing`

Возвращает `pending`, `applied`, `ignored`, `rejected` и `oldest_pending_at`. Последнее поле равно `null`, когда ожидающих наблюдений нет.

### `GET /api/v1/admin/domain-events`

Возвращает внутренние записи об изменениях сообщества, состава, серверов и применённых наблюдениях. Поддерживает фильтр `community_id` и пагинацию `offset` и `limit`. Записи упорядочены по убыванию `occurred_at`, затем `id`.

### `POST /api/v1/admin/telegram-notifications/send`

Отправляет до `limit` ожидающих уведомлений. По умолчанию 20, диапазон от 1 до 100. Ответ содержит счётчики `sent`, `failed`, `uncertain` и `canceled`. Активная отправка идентифицируется по записи наблюдения. После тайм-аута или неоднозначного ответа Telegram итог фиксируется как `uncertain`. Уведомление, отправка которого уже началась, может прийти после отключения подписки.

## Размер тела HTTP-запроса

Для маршрутов с JSON-телом предел по умолчанию составляет 131 072 байта (128 КиБ), включая вход через Telegram и `POST /api/v1/callbacks/server-status`. Для `POST /api/v1/callbacks/events` допускается 1 048 576 байт (1 МиБ). Учитываются все байты тела, включая пробелы и синтаксис JSON. Размер ровно на границе допустим. Проверки полей и полномочий продолжают действовать.

Caddy ограничивает чтение потока, а API проверяет размер до разбора JSON, в том числе без `Content-Length`. При превышении клиент получает HTTP 413 и код `request_body_too_large`. Для создания публикации действует предел 128 КиБ с кодом `community_post_too_large`, для загрузки изображения — 2 МиБ с кодом `community_post_image_too_large`. Ошибка содержит `error.request_id` и заголовок `X-Request-ID`.
