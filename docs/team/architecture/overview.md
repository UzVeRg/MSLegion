# Архитектура MSLegion

## Как устроен backend

MSLegion развивается как модульный монолит. Backend запускается одним приложением FastAPI, а границы предметных областей проходят внутри `backend/app/modules/`.

```text
HTTP-запрос → маршрутизатор → сервис → репозиторий → PostgreSQL
```

| Область | Ответственность |
| --- | --- |
| [Точка входа](../../../backend/app/main.py) и [общий маршрутизатор](../../../backend/app/api/router.py) | Сборка FastAPI, подключение модулей, проверки состояния приложения |
| [Пользователи](../../../backend/app/modules/users) | Создание, получение и список пользователей по административному ключу |
| [Интеграции](../../../backend/app/modules/integrations) | Приём входящих событий, обработка дубликатов и просмотр истории |
| [Администрирование](../../../backend/app/modules/admin) | Состояние базы и счётчики записей |
| [Ядро](../../../backend/app/core) | Конфигурация, сессии БД, ключи API, ошибки, журналирование и контекст запроса |
| [Миграции](../../../backend/alembic/versions) | Версионирование схемы PostgreSQL |

Маршрутизатор принимает запрос и формирует ответ. Сервис отвечает за прикладное поведение, а репозиторий — за операции с данными. Модули могут использовать только нужные им слои. Ошибки предметной области определяйте в её модуле. Ядро задаёт общий формат HTTP-ошибки. Транзакцию записи открывает сервис. Репозиторий выполняет SQL в переданной сессии, а уникальные ключи PostgreSQL разрешают конкурирующие вставки. При работе с PostgreSQL используйте асинхронный ввод-вывод и отдельный `AsyncSession` для каждой параллельной задачи. Общая база ORM находится в `app/core/models.py`. При добавлении новой модели подключите её модуль в `alembic/env.py`, чтобы автогенерация видела таблицу. Изменения схемы проводите через Alembic.

## Целевая архитектура

- Основной пользовательский интерфейс — один Telegram Mini App. Каталог из 50 исходных идей используется для планирования возможностей продукта.
- Telegram-бот открывает Mini App и может доставлять уведомления или служить входом в поддержку. Прикладное поведение остаётся в сервисах backend.
- PostgreSQL хранит постоянные данные. Кэш, обработчики фоновых задач и отдельные сервисы добавляются под конкретные требования.

### Решения для первого пользовательского входа

Эти решения приняты для P0. Реализованные маршруты перечислены в [справочнике HTTP API](../reference/api.md).

| Вопрос | Решение и причина |
| --- | --- |
| Откуда берётся личность? | Модуль входа получает исходную строку `initData` и проверяет подпись, срок действия и допустимое расхождение часов. Только затем использует Telegram ID. Бизнес-модули ссылаются на `users.id` (UUID). [Правила Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) |
| Как поступить с прежними записями? | Существующие `telegram_id` могли быть введены вручную через API. При миграции их привязка получает статус неподтверждённой. Если проверенный Telegram ID совпал со старой записью, администратор сверяет её принадлежность до передачи прежних данных и прав. До сверки вход в эту запись закрыт. При первом входе новой личности создание и подтверждение привязки выполняются атомарно. |
| Как работает сессия? | Для монолита используем отзываемую серверную сессию в PostgreSQL. Mini App хранит случайный непрозрачный токен в памяти и передаёт его в заголовке Authorization по HTTPS. В БД хранятся хеш токена, внутренний UUID пользователя, срок действия и состояние отзыва. Это позволяет завершить доступ при выходе или блокировке. |
| Где проверяются права? | Маршрут собственного профиля получает владельца из сессии. Служебное управление записями остаётся за административной границей. Бот и Mini App вызывают те же прикладные сценарии, секреты интеграций и администрирования хранятся на сервере. |

### Приём и обработка событий

Сейчас успешная квитанция означает, что событие сохранено в PostgreSQL. Пара `source` и `event_id` принадлежит одному логическому событию. Общий ключ приёма рассчитан на доверенный контур. До подключения независимых отправителей потребуется ограничить доступ каждого его источниками. Для предметной обработки предстоит отдельно определить эффект, состояние обработки и правила повтора после сбоя. [Порядок работ](../planning/roadmap.md)
